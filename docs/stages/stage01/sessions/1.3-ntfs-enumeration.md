# stage01/1.3 — ntfs-enumeration
Date: 2026-10-19 · Issue: #3 · PR: #20 · Verification reached: V3 (elevated CI); V4 pending the owner's run

**Context**: wave 1 spike for G1/Q-16. Enumerate an NTFS volume with `FSCTL_ENUM_USN_DATA`, query the journal, parse records with pure functions, and measure time and memory. Raw records stay local to `ntfs`; `Source` comes in 2.2.

## What changed
- `crates/ntfs/Cargo.toml`: `windows` (workspace 0.62.2) as a `cfg(windows)` target dependency, with features added at crate level (Foundation, Security, Storage_FileSystem, System_IO, System_Ioctl, System_ProcessStatus, System_Threading). Also `thiserror` and `tracing`. The root `Cargo.toml` is unchanged.
- Pure modules, compiled on every platform and tested on Linux and Windows:
  - `src/record.rs`: parsers for `USN_RECORD_V2`/`V3` (`parse_record` returns a zero-copy `UsnRecord<'a>`), `FSCTL_ENUM_USN_DATA` output (`parse_enum_output` gives the next start FRN and a `RecordIter`), `USN_JOURNAL_DATA_V0/V1/V2` (`parse_journal_data` gives a `JournalInfo`) and `MFT_ENUM_DATA_V1` encoding. There are also `record_number`/`sequence_number` helpers and a `build` module that synthesises records (2.2 can reuse it for journal fixtures). Every length and offset is validated. Record-local errors (unknown version, bad name span, non-64-bit V3 ID) skip that one record; structural errors (bad `RecordLength`) end the batch.
  - `src/name.rs`: `NtfsName`, a lossless WTF-8 name (see Decisions).
  - `src/chain.rs`: `ParentChainReport::compute(&[(frn, parent)], root)`. It's O(n), iterative, and counts resolved, orphaned and cyclic chains.
  - `src/drive.rs`: drive-letter parsing (`C`, `C:`, `C:\`, `\\.\C:`, `\\?\C:`).
  - `src/error.rs`: `Error` (`InvalidVolume`, `NotNtfs`, `NotElevated`, `JournalDeleteInProgress`, `Stalled`, `Os{op,code,message}`, `Parse`) and `ParseError`, plus Win32 code constants.
- Windows-only modules:
  - `src/volume.rs`: `volume_info()` (`GetVolumeInformationW`, no elevation needed). `Volume::open` checks the file system first (`NotNtfs`), then opens `\\.\X:` with **`GENERIC_READ` only**; a denied open becomes `NotElevated`. `root_frn()` uses `GetFileInformationByHandle` on `X:\`. `query_journal()` returns `Ok(None)` when no journal is active, and the crate never creates one. `enumerate()`/`enumerate_with(EnumOptions)` return an `Enumerator` with one reusable 8-byte-aligned buffer (1 MiB by default). The enumerator works either as an `Iterator<Item = Result<RawRecord>>` or through the zero-copy `next_batch()`. `EnumStats` tracks batches, records, skipped records, bytes and `kernel_time`.
  - `src/process.rs`: `process_memory()` returns the working set and peak working set.
  - All 9 `unsafe` blocks plus one `unsafe impl Send for Volume` carry `// SAFETY:` comments. `#![allow(unsafe_code)]` is set in `lib.rs` only.
- Tests: 32 unit tests, covering the V2/V3 fixtures hand-encoded from `winioctl.h` and cross-checked against the builder, truncation at every length, 20k random mutations, round trips of every UTF-16 unit and of surrogate pairs, and parent-chain cases.
- `crates/ntfs/tests/enumerate_volume.rs` (Windows): 3 unelevated tests (C: is NTFS, malformed args, missing drive) and 2 `#[ignore]` elevated tests. `enumerates_system_volume` runs three passes back to back so they never compete for the disk. `query_journal_on_system_volume` checks the journal. Measurements go to the CI log as `[ntfs-measure]` lines.
- `crates/ntfs/examples/enum_volume.rs` prints the volume, journal, root FRN, record count, kernel vs user time, working set and peak, and the parent-chain ratio. Options are `--buffer-kib N` and `--count-only`.
- `Cargo.lock` is committed for the first time (the bootstrap note asked the first building session to do this).

- Process baseline was 5.2 MiB. Kernel output was 144 MiB in 144 batches. 207,883 entries were directories. Names total 33.0 MB as WTF-8 (24.6 B average). **0 records** were skipped and **0 names** were invalid UTF-16.
- Parent chains: root FRN `0x0005000000000005`. **The root itself is not returned by `FSCTL_ENUM_USN_DATA`**, but 45 records have it as parent. 1,343,303 of 1,343,310 chains resolve (**99.9995%**). 7 are orphans: NTFS metadata, explained below. There are 0 cycles, and the chain check took 3.1 s in the debug build.
- Journal on C: is active: max size 32 MiB, record versions 2 to 4.
- How to read these numbers:
  - The first read is **disk-bound**: 90% of the time is in the kernel, which reads about 1.3 GB of MFT for 1.34M records from a cloud disk.
  - The warm passes show the API's real CPU cost: about 2.6 s of kernel time per 1.34M records, plus our parsing at about 0.6 s in a debug build (less in release).
  - Buffer size barely matters between 64 KiB and 1 MiB.
  - An earlier run (39261165050) took 142 s for the first read because two cold enumerations ran in parallel. That's why the passes are now serialized.
- Memory: enumeration itself streams, so its own memory is the buffer (1 MiB). The 161 MiB peak is the test keeping 1.34M owned `RawRecord`s, about 100 B each in the debug build, plus the link vector. That's an upper bound for "collect everything naively". The 2.1 name index will be much denser.

- **Orphans** (run 39262404515): only one record's parent is missing: `$RmMetadata` (`frn 0x1000000000001b`), whose parent is `$Extend` (record 11, `0xb00000000000b`). Like the root, `$Extend` is not returned by the enumeration. The other 6 orphans sit under `$RmMetadata` (`$TxfLog`, `$Txf`, …). So all user-visible files resolve, and the only gap is NTFS metadata, which an index should hide anyway.
- **Variance of the first read**: the same pass 1 took 61.3 s in run 39262404515, compared with 40.6 s above (57.1 s of it in the kernel). Cloud disk throughput varies between runs. Warm passes are stable: 3.35 s total and 2.62 s in the kernel.

## Decisions proposed
- **Name encoding: WTF-8 (`NtfsName`)**, not `String` or `OsString`.
  - Why: it's lossless (unpaired surrogates survive, so two names never collide) and byte-identical to UTF-8 for valid names. ASCII names take half the space of UTF-16. It works on Linux, unlike `OsString::from_wide`, and matches `OsStr::as_encoded_bytes` on Windows (tested).
  - Consequence for 2.1: the string pool can store WTF-8 bytes directly, and case-folding works on UTF-8 for 100% of the names seen on C:.
- **Ask for `USN_RECORD_V2` only** (`MFT_ENUM_DATA_V1`, min = max = 2). NTFS file references are 64-bit, and V2 records are 16 bytes smaller than V3. V3 is still parsed, and narrowed to 64 bits (or rejected) if the system returns it, so 2.2 can read journal records of either version.
- **Root FRN comes from `GetFileInformationByHandle(X:\)`**, not from the enumeration, which never returns the root. Downstream (2.1/2.2) must seed the root entry.
- **Q-16 (preliminary, for G1):** keep `FSCTL_ENUM_USN_DATA` for M0. On CI the warm cost is about 2.6 s of kernel time per 1.34M records, and the cold cost is dominated by MFT I/O. Raw `$MFT` parsing would read the same bytes. Its potential wins are larger sequential reads on a cold cache, plus sizes and timestamps in the same pass. Decide after the owner's V4 numbers. If a cold run on the owner's SSD stays under about 10 s for their largest volume, keep the USN API. Final call in 4.3.

## Deviations / contract changes
- None. No frozen contracts exist yet; this crate doesn't use `core`/`source` types (2.2 does).
- "Captured fixtures" are hand-encoded from the documented `winioctl.h` layouts, not dumped from a real volume, so no real file names from the owner's disks get committed. Real kernel output is checked by the elevated test instead: 1.34M records, 0 parse failures.

## Follow-ups
- **Owner (V4, feeds G1 and Q-16)**: run the example on the GIS workstation. Steps:
  1. Install Rust with rustup and VS Build Tools (the "Desktop development with C++" workload). `rust-toolchain.toml` pins 1.99.
  2. Get the code: `git fetch origin` then `git switch s01/w1-3-ntfs-enumeration` (or `develop` once this PR is merged).
  3. Open **PowerShell as Administrator** (Start → right-click PowerShell → Run as administrator) and `cd` to the repo.
  4. Build once: `cargo build --release -p whereabouts-ntfs --example enum_volume`.
  5. **Cold run**: reboot, open the elevated PowerShell, and before anything else run `cargo run --release -p whereabouts-ntfs --example enum_volume -- C:`. Note whether *Everything* is running: it reads the MFT at startup and warms the cache.
  6. **Warm run**: run the same command again, then once more with `-- C: --count-only`.
  7. Repeat steps 5 and 6 for the volume that holds the GIS data (e.g. `-- D:`).
  8. Paste the complete output into issue #3 or this PR, with the disk type (NVMe/SATA SSD/HDD) and the volume's rough file count as Everything shows it.
  - The example is read-only: it opens the volume with read access, never creates a journal, and writes nothing. Without elevation it stops with "access denied … needs an elevated (administrator) process".
- **2.1 nameindex**: seed the root entry from `Volume::root_frn()`. Expect a few orphans (`$Extend\$RmMetadata\…`, because `$Extend` is not enumerated) and use the orphan guard (or seed `$Extend` the same way as the root). Use `next_batch()` for zero-copy ingestion.
- **2.2**: reuse `record::parse_record`/`RecordIter` for `FSCTL_READ_USN_JOURNAL` output (V2 and V3 are both handled, `reason` and `usn` are parsed). Add `ERROR_JOURNAL_ENTRY_DELETED` to `error::win32`. `JournalInfo` already carries `journal_id`, `first_usn`, `next_usn` and `max_usn` for the checkpoint.
- **4.3**: release-build CI numbers and a comparison against Everything. A CI job running `enum_volume` in release would give cleaner CPU numbers (that's a CI change, outside this scope).
- **Hard links**: enumeration returns one name per MFT record. Extra names are not reported, as already documented for M0.
- Mount points and `\\?\Volume{GUID}\` volume paths are not supported yet; only drive letters work.
