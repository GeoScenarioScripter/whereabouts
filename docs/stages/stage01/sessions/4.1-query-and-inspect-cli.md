# stage01/4.1 — query-and-inspect-cli
Date: 2026-11-09 · Issue: #14 · PR: #66 · Verification reached: V3 (Windows CI)

**Context**: consumes the frozen nameindex, grouper, catalog and shared 3.3 extraction
contracts. Adds the usable query/inspect commands while preserving `index`.

## What changed
- `crates/query/src/lib.rs`: reusable dedicated rayon search pool; literal case-folded
  names → member FRNs → deduplicated datasets; format/EPSG/R*Tree filters retain
  same-layer semantics and antimeridian splitting. Exact > prefix > substring
  (best member or display stem), newest mtime, then ID; limit applies last.
- Selective terms use indexed member lookups. Broad terms (>256 names and >25% of
  candidate datasets) inspect batched catalog summaries instead of executing SQL per
  non-GIS file. Small filtered candidate sets (at most 256) read only those summaries.
  Ranking and limits precede full layer/CRS/raster hydration. Empty text skips the filename scan. Orphan/cyclic
  anchors and matching orphan members are hidden. No frozen contract changed.
- `crates/cli/src/main.rs`: query loads `<db>.names`, opens the catalog read-only,
  and requires one matching checkpoint within a consistent catalog read snapshot.
  `--snapshot`/`--volume-id` support distinct per-source snapshots. JSON contains full
  dataset/layer records; tables escape controls. CLI index behavior is preserved.
- `crates/cli/src/inspect.rs`: canonical path → bounded sibling/folder directory
  view → grouper → `indexer::extract`; member paths resolve to owning datasets,
  GDB internal paths to the enclosing folder. Discovery stops at 100,000 entries,
  does not follow symlink entries, and readers retain their normal byte/time limits.
  Inspect creates no catalog or dataset sidecars. Default output includes layer
  CRS, native/WGS84 bounds and raster facts. JSON grouping IDs are temporary.
- `crates/cli/README.md`: command semantics, format codes, snapshot handling,
  inspect status/identity conventions and repeatable startup measurement.
- Portable CLI tests: ranking/deduplication, both planner paths, limits, formats,
  antimeridian boxes, same-layer EPSG+bbox, orphan suppression, invalid arguments,
  corrupt/missing/mismatched/ambiguous snapshots; inspect SHP/GPKG/TIFF facts,
  unchanged bytes/mtime/directory entries, malformed contents and GDB internals.
- Existing `index_vhd.rs` now invokes query/inspect processes, compares inspect
  layers/status to indexed metadata, tests member/format/limit/spatial filtering,
  and measures startup to the first dataset row. Existing restart/edit tests remain.
- Dependencies activate existing workspace rayon/serde_json/tempfile entries only;
  review adds existing workspace rusqlite as a CLI dev-dependency for a corruption fixture.

## Decisions proposed
- CLI rejects mismatched checkpoint state rather than returning mixed results;
  checkpoint matching, filters and record loads share one read transaction. Multi-source
  ambiguity requires explicit snapshot/volume selection.
- Inspect uses volume 0 and ephemeral discovery IDs in JSON, documented as not
  catalog identities. Reader errors are records with `error` status; command/setup
  failures use nonzero exit. Simple ranking follows the session spec, not Q-17's
  deferred spatial relevance model; Q-11 syntax remains deferred.
- Rank lightweight catalog summaries, then hydrate only the selected result page. The
  summary includes identity, display name, mtime and member FRNs, without layer metadata.

## Deviations / contract changes
- Wave review authorized additive `Catalog::read_snapshot`, `DatasetSummary`,
  `dataset_summary` and `dataset_summaries` APIs and catalog regressions, beyond the original
  query/CLI write scope. Existing method signatures, schema and
  core/source/nameindex contracts are unchanged. QueryEngine and CLI use nested read views
  on the same connection; WAL writers remain unblocked and output happens after release.

## Follow-ups
- The lightweight ranking part of #47 is now implemented. Selective terms still use
  one indexed lookup per matching member; a batch member lookup remains a possible
  optimization. Broad queries still scan lightweight summaries and scale with GIS count.
- Snapshot v1 startup rebuilding remains the dominant one-shot CLI cost; a resident
  query service and snapshot v2 are later-stage work. Hard links retain M0's one-name
  limitation. No real-volume Q-18 claim is made from synthetic measurements.

## Wave review: GIS candidate scaling

The original five-GIS-dataset fixture hid full metadata hydration costs. A second
release harness uses 10,000 and 100,000 synthetic one-layer Shapefile datasets/names,
limit 100, one warm-up then five reused-engine calls per term. Hardware: Windows
10.0.26300, Intel64 Family 6 Model 189 Stepping 1, eight logical CPUs. These are
synthetic V2 diagnostics, not V4 or statistically robust tail-latency estimates.
The second value below is the maximum of five samples (original console label was p95).

Before summary hydration, p50 / max milliseconds:

| Datasets | Exact `road_000001` | Intermediate `road_000` (1,000 hits) | Broad `road` | Empty |
|---:|---:|---:|---:|---:|
| 10,000 | 0.140 / 0.278 | 15.610 / 19.247 | 210.506 / 214.869 | 120.489 / 122.676 |
| 100,000 | 0.180 / 0.252 | 62.788 / 118.829 | 6436.721 / 8880.686 | 1341.172 / 1638.511 |

The selective/broad/empty baseline ran in a reserved window with sibling heavy work
paused. The separate intermediate baseline may overlap a sibling's finishing tests;
no intermediate before/after speedup ratio is claimed.

After summary hydration, with sibling builds/tests explicitly confirmed idle:

| Datasets | Exact `road_000001` | Intermediate `road_000` | Broad `road` | Empty |
|---:|---:|---:|---:|---:|
| 10,000 | 0.117 / 7.064 | 15.114 / 25.967 | 75.029 / 141.104 | 17.693 / 78.158 |
| 100,000 | 0.102 / 0.229 | 35.349 / 36.501 | 192.530 / 203.368 | 313.448 / 358.417 |

At 100k datasets, broad median dropped from 6436.721 to 192.530 ms and empty median
from 1341.172 to 313.448 ms. Host noise remains visible even with sibling heavy work
paused. Summary scanning/ranking still scales with GIS dataset count; these figures
do not establish instant end-to-end search or resolve Q-18. No intermediate speedup
ratio is claimed because its baseline may have been contended.
