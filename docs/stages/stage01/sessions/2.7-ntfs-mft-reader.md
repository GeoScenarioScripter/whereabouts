# stage01/2.7 — ntfs-mft-reader
Date: 2026-10-27 · Issue: #31 (related: #29) · PR: #39 · Verification reached: V3 (elevated CI, `C:`); V4 requested from the owner

**Context**: added at gate G1 after the owner's D: run (1.44M records in 41.0 s, 40.8 s of it inside `FSCTL_ENUM_USN_DATA`). Reads `$MFT` directly in large sequential chunks and yields the same `RawRecord` as the USN enumeration, so `Source` and its consumers do not change. Depends on 1.3 (`RawRecord`, `NtfsName`, D-31) and 2.2 (`NtfsVolumeSource`). Which method is the default is **not** decided here (4.3 decides Q-16).

## What changed
- `crates/ntfs/src/mft.rs` (pure, all platforms): bounded parsers.
  - `parse_volume_data` for `NTFS_VOLUME_DATA_BUFFER` into a validated `VolumeGeometry` (power-of-two sector, cluster and record sizes, `$MFT` start inside the volume).
  - `apply_fixups`: signature, update sequence array and per-sector torn-write check.
  - `parse_record_header`.
  - `Attrs`: attribute iterator that yields one `Err` and stops on a lying length.
  - `decode_runlist`: field sizes 1..=8, no zero-length run, signed LCN deltas with checked arithmetic, LCNs inside the volume, VCN overflow rejected, at most 2^20 runs.
  - `parse_standard_info`, `parse_file_name`, `AttrListEntries`.
- `crates/ntfs/src/mft_scan.rs` (pure, generic over `ByteSource`): `MftScanner::open` and `scan`.
  - `open` reads record 0 at `MftStartLcn` and decodes `$DATA` (following an `$ATTRIBUTE_LIST` into extension records when `$MFT` itself is fragmented) and `$BITMAP`.
  - `scan` reads the `$MFT` stream in 4 MiB chunks (configurable), skips chunks the bitmap marks free, and turns every in-use *base* record into a `RawRecord`.
  - `MftScanStats` counts torn, malformed, not-`FILE`, no-name and extension records, hard-linked files, and bytes and time spent reading.
- `crates/ntfs/src/mft_build.rs` (tests or `test-fixtures`): hand-built records with update sequence arrays, attributes, runlists, and a whole synthetic volume image.
- `crates/ntfs/src/volume.rs` (additive): `Volume::geometry()` (`FSCTL_GET_NTFS_VOLUME_DATA`), `Volume::read_raw()` (`ReadFile` at an offset; unaligned requests are widened to 4 KiB, so the large aligned chunks are read straight into the caller's buffer), `Volume::open_mft()`, `impl ByteSource for Volume`. There are 2 new `unsafe` blocks (`DeviceIoControl`, `ReadFile`), each with a `// SAFETY:` comment.
- `crates/ntfs/src/source.rs`: `EnumerationMethod { UsnApi (default), RawMft }` and `SourceOptions::{enumeration, mft_chunk_bytes}`. The raw path sends the synthesised root first and the same checkpoint (taken before enumerating, D-29), then streams the scan. `RawMft` is an internal switch, not a recommendation.
- `crates/ntfs/src/error.rs`: `Error::Mft { volume, source: MftError }` (the enum is `#[non_exhaustive]`; `source_error` maps it to `SourceError::Io`).
- `crates/ntfs/examples/enum_volume.rs`: `--mft` and `--chunk-mib N`, printing the same figures as the USN mode.
- `crates/ntfs/tests/mft_volume.rs`: one `#[ignore]` elevated test (see Verification).
- `.github/workflows/ci.yml` (**shared file, 2 small changes**):
  - the elevated step now uses `--no-fail-fast`, so a flake in `journal_vhd` no longer hides the later test binaries;
  - a new Windows step runs `enum_volume` in release on `C:` (bash with `set -e`, so a failure or a lossy raw scan fails the job): USN `--count-only` and `--mft --count-only` only (see Review fixes).

## How equivalence with the USN API is defined (and what we found)
Record sets are compared on FRN with sequence number, parent FRN, name (WTF-8) and the directory bit. Rules that make them agree:
- **Name choice.** The first `$FILE_NAME` in the Win32 or Win32+DOS namespace wins, else the first POSIX one. DOS-only names are never reported. For all 52,165 hard-linked files on the runner the USN API reported the same (parent, name) as this rule: 0 differences. USN's pick was not obviously "first Win32", so this may be luck of the data; the rule is documented, not guaranteed.
- **Extension records.** A file whose `$FILE_NAME` attributes live in extension records (via `$ATTRIBUTE_LIST`) gets them from the extension records seen during the same sequential pass; files whose extension records come *later* are held back and delivered after the pass. A first version read each extension record with a random read (15.7k of them took 4.9 of the 5.4 s of read time); the cache removed all of them. A random-read fallback remains for an exhausted cache (`ext_cache_bytes`, default 128 MiB).
- **Attributes.** `$STANDARD_INFORMATION` attributes, masked to the low 16 bits (NTFS-internal bits such as the directory-index flag `0x10000000` and `0x80000000` are not reported by the USN API), plus the directory bit from the record header; `FILE_ATTRIBUTE_NORMAL` (`0x80`) when nothing is set, as the USN API does.
- **Left out** (`skip_reserved`, used by `NtfsVolumeSource`): the reserved system records 0..=15 except the root, the children of `$Extend` (record 11) except the `$RmMetadata` directory, and `$RmMetadata\$Repair`. That is exactly what the USN API omits, on `C:` and on a fresh VHD. Without `skip_reserved` the scan yields 17 more records on `C:`.
- **`usn`/`timestamp`** carry `$STANDARD_INFORMATION`'s last USN and last-write time. They mean something different than in a USN record, so they are not part of the equivalence.

## Decisions proposed
- **Q-16 evidence (decision stays with 4.3 and the owner).** On the CI runner's `C:` (1.35M records, 1.34 GB of `$MFT`, 512 B sectors, 1 KiB records, cloud disk), release build:

  | | USN API | Raw `$MFT` |
  |---|---|---|
  | First read in the job (cold) | **34.0 to 58.4 s** in the kernel (`enumerate_volume` pass 1 in four runs: 36.2, 41.3, 48.1, 61.7 s total) | **5.4 to 5.8 s** reading, 6.1 to 6.9 s total |
  | Repeat (warm) | **2.2 to 2.7 s** kernel, 2.5 to 2.9 s total | 5.3 to 5.8 s reading, 6.0 to 6.9 s total |
  | User-code time | 0.02 s (count-only), 0.29 s (collect) | 0.5 to 0.7 s |
  | Memory (collect owned) | peak 160.6 MiB | peak 163.9 MiB |

  So on this runner the raw reader is about 6 to 10 times faster cold and about 2.3 times slower warm. The raw time is flat at roughly 245 MB/s across 1, 4 and 32 MiB chunks and does not shrink on a second pass, so it is the throttled disk, not call overhead or our parsing (user code is 0.5 to 0.7 s). Raw volume reads are not served from the file system's `$MFT` cache, which is why USN wins warm. The cold USN figure on this runner includes the OS cache being empty for `$MFT`; CI cannot drop caches, so "cold" means "first access in the job". On NVMe the raw read should approach parse speed (about 0.6 s per 1.35M records); the owner's D: numbers decide.
  - Proposal for 4.3: use raw `$MFT` for the first (cold) index of a volume and the USN journal for changes, subject to the owner's V4 cold run on D:. Keep the USN API as the fallback on any `Error::Mft` (unsupported layout, ReFS, damaged `$MFT`).
- **Sizes and timestamps can come from the same pass (input to stage02): yes, at no extra I/O.**
  - `$STANDARD_INFORMATION` is resident in the base record we already parse; it holds creation, write, MFT-change and access times (the scanner already reads the write time and attributes).
  - `$DATA` sizes come from the unnamed `$DATA` header in the same record: the logical size for a non-resident `$DATA`, or the value length for a resident one, plus the allocated size.
  - Caveats: for files whose `$DATA` lives in an extension record (large or fragmented files with an `$ATTRIBUTE_LIST`) the size comes from the extension record, which the pass already remembers for names (about 1.2% of files on the runner); directories have no `$DATA`; `$FILE_NAME` also carries sizes and times but they lag behind.
  - The USN API gives neither sizes nor times, so with it stage02 would need one `stat` per file.
- **Pending records are delivered after the sequential pass** when their extension records come later in the table. No consumer should rely on `$MFT` order.

## Review fixes (PR #39 review)
`RawMft` is now **strict**: a scan that cannot account for every in-use record returns an error and the caller falls back to the USN API.
1. **Torn records**: each is read again once, after the sequential pass (`torn_retried`, `torn_recovered`; tested with a source that tears a record once). `enumerate_raw_mft` returns `Err(Error::MftIncomplete)` when `lost() > 0`; `no_name` is counted and reported but is not a loss.
2. **Complete loss accounting**: `lost()` = torn + malformed + `not_file_in_use` (bitmap-covered slots without a `FILE` signature) + `extension_errors`. Now counted: a bad `$ATTRIBUTE_LIST`, a bad `$STANDARD_INFORMATION` (record kept, counted as malformed), a malformed `$FILE_NAME` (base: malformed; extension: extension error), list entries pointing outside the table. A second non-resident list extent no longer replaces the first. The per-file extension cap went from 64 to 4096 (a file with hundreds of hard links legitimately has many); hitting it is a loss.
3. **Truncated table**: a runlist that covers less than the declared size is an error. `initialized_size < real_size` is allowed, logged (`warn`) and counted (`uninitialized_slots`).
4. **Sink semantics**: documented on `enumerate`/`EnumerationMethod::RawMft` (discard the sink's records before falling back). `Error::Mft` and `Error::MftIncomplete` say how many records were delivered; `last_enumerate_stats` is set on every error path.
5. **Unflushed pages**: the raw checkpoint starts replay `SourceOptions::raw_replay_margin` (default 1 MiB) of journal before the position taken at the start (`checkpoint::replay_start`, unit-tested arithmetic). The first version passed `next_usn - margin` straight to the kernel; the new VHD test (`raw_mft_enumeration_matches_usn_and_replays_a_margin`, margin 700 bytes) showed that `FSCTL_READ_USN_JOURNAL` rejects a start USN that is not a record boundary (`ERROR_INVALID_PARAMETER`), so the source now walks the journal from `first_usn` in 64 KiB reads and snaps the position to the last record at or before the target (`replay_boundary`; any trouble falls back to `first_usn`, which only replays more). The test also checks that the raw enumeration equals the USN enumeration on that volume and that the replay reports (3 events) only files the scan already listed. `FILE_FLAG_NO_BUFFERING` was **not** adopted: it would need a second handle and sector-aligned buffers, it does not help with unflushed metadata (those pages live in the `$MFT` file's cache, not the volume's), and the measured raw time is flat across 1/4/32 MiB chunks and does not benefit from caching, so there is nothing to gain.
6. **Bounds**: deferred files are capped at 64 MiB (beyond it a file is finished at once with direct reads); `$ATTRIBUTE_LIST` loads count in `reads`/`bytes`/`read_time`, and the list limit dropped from 16 MiB to 1 MiB.
7. **Equivalence test**: asserts `lost() == 0` and `extension_errors == 0` after the retry, `skipped == 0` for the raw Source, `only_usn:UNEXPLAINED == 0`, `only_mft:UNEXPLAINED == 0`, no attribute-only differences, `differ:hard_link == 0` (the name rule must agree on every hard-linked file), churn built only from create/delete/rename events (a plain `Modified` excuses nothing) with `churn_complete` required, and at most 5 unexplained name/parent differences (a hard link added or removed during the run is not reported by the 2.2 journal source). The 1/5000 tolerance is gone. The Source wiring is compared as FRN sets, not counts. This also exposed that the first `$Extend` rule was inexact (`$RmMetadata` is listed by the USN API, `$Repair` is not); the rule now matches on `C:` and on a fresh VHD.
8. **CI**: the release step is bash with `set -euo pipefail` and runs only `enum_volume -- C: --count-only` and `-- C: --mft --count-only`. `enum_volume --mft` exits non-zero when `lost() > 0`. `--no-fail-fast` stays on the elevated test step.
9. **Flaky 2.2 test** `checkpoint_older_than_first_usn_requires_rescan`: NTFS lets the journal grow to about 40 MiB before trimming, so it filled the 64 MiB VHD. It now runs on a 512 MiB (expandable) VHD; the test is otherwise unchanged and no slower.

- **4.3**: decide Q-16 with the owner's D: numbers; also decide whether the cold path should overlap I/O with parsing.
- **Overlapped read-ahead** (spec: optional) was not done. Parsing is 0.5 to 0.7 s per 1.35M records (release), so overlap would cut at most that from the cold time; it matters only if the disk is fast enough (NVMe) for read time to be of the same order. `Volume` would need `Sync` and `MftScanner::scan` a prefetch thread.
- **Not handled**: `$BITMAP` or `$DATA` pieces of `$MFT` in extension records beyond the described `$DATA` continuation (a short bitmap falls back to the record header flag); compressed or sparse `$MFT`; 4Kn disks and 4 KiB records are covered by unit tests only (the raw read path widens to 4 KiB; the CI disk has 512 B sectors); ReFS (`NotNtfs` at open).
- **Hard links**: the scan counts them (52,165 files on the runner) and could report every name, which the USN API cannot; stage02 decides if the model should hold all links. Separately, the 2.2 `changes` path reports nothing when only a hard link is added or removed, so one run showed a Defender file whose parent differed between the two passes without a journal event (3 files in run 2).
- **Flake in 2.2's `journal_vhd`**: `checkpoint_older_than_first_usn_requires_rescan` failed with `StorageFull` (the 64 MiB VHD fills while churning for the wrap) in 2 of 4 first CI runs of this PR; a re-run passed. It is not touched by this PR and needs a fix in the 2.2 owner's area (4.2 or a hotfix): bound the churn by free space, or use a larger VHD.
- **#29**: the new release step records the timings but does not assert anything; turning it into a tracked job is left to 4.3.
