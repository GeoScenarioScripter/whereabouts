# stage01/2.2 — ntfs-journal-source
Date: 2026-10-20 · Issue: #6 (also #24) · PR: #34 · Verification reached: V3 (elevated CI, VHD volume)

**Context**: builds on 1.1 (`Source`, `Checkpoint`, D-29) and 1.3 (enumeration, `RecordIter`, `enum_step`, D-31). Spec: `FSCTL_READ_USN_JOURNAL` polling, reason → `SourceEvent` folding, rescan detection, `NtfsVolumeSource: Source` and a VHD test volume for CI.

## What changed
- `crates/ntfs/src/journal.rs` (pure, all platforms):
  - `reason::*` holds the `USN_REASON_*` flags and `MODIFIED_MASK`.
  - `encode_read_usn_journal_data_v1` builds a non-blocking read with every reason, `ReturnOnlyOnClose = 0` and V2 records only.
  - `read_step` reuses 1.3's `enum_step`, because both replies start with an 8-byte cursor.
  - `file_record` converts a parsed record into a `FileRecord`.
  - `Coalescer` folds one batch per file. The rules are in the module docs. In order of precedence:
    - Delete gives `Deleted`, even for a file created in the same batch, because enumeration may have seen it.
    - Create gives `Created` under the final name.
    - Old name + new name gives `Renamed` with the first old (parent, name).
    - Content, attribute, stream or link reasons give `Modified`, emitted after `Renamed` when both apply.
    - Security, object ID and indexing reasons are ignored.
  - Events are ordered by each file's first record in the batch.
- `crates/ntfs/src/checkpoint.rs` (pure):
  - `NtfsCheckpoint` is payload v1: volume serial, a journal-present flag, journal ID, next USN, and up to 64 pending renames. It is at most about 49 KiB and every length is validated on decode.
  - `assess()` maps serial mismatch, no journal now, journal ID change (or a journal that appeared), USN < `FirstUsn`, and USN > `NextUsn` to the matching `RescanReason`.
- `crates/ntfs/src/source.rs` (Windows): `NtfsVolumeSource` with `open`/`open_with(SourceOptions)`, `identity()` (kind `ntfs`, key = volume GUID path, label `X:`) and `root()`.
  - `enumerate`: takes the checkpoint from `query_journal` **before** enumerating (D-29), sends a synthesised root record first (own parent, empty name, `DIRECTORY`), then streams `next_batch()` zero-copy.
  - `changes`: reads until caught up, or until `max_batch_bytes` (32 MiB by default, so a long backlog arrives in bounded batches). `last_change_stats()` reports the counters.
  - Error mapping:
    - `ERROR_JOURNAL_ENTRY_DELETED` → `JournalWrapped`.
    - Journal not active or being deleted → `JournalMissing`.
    - A malformed or foreign checkpoint → `CheckpointMismatch`.
    - A 128-bit file ID → `SourceError::Unsupported` (#24).
    - `NotElevated` → `AccessDenied`.
- `crates/ntfs/src/volume.rs` (additive only, `Enumerator` unchanged): `Volume::read_journal(start_usn, journal_id, &mut [u64]) -> &[u8]` and `Volume::volume_guid_path()`. There are 2 new `unsafe` blocks, each with a `// SAFETY:` comment.
- `crates/ntfs/src/error.rs`:
  - Win32 codes: `ERROR_JOURNAL_ENTRY_DELETED` (1181) and `ERROR_INVALID_PARAMETER`.
  - `Error::JournalNotActive`, `Error::JournalEntryDeleted`.
  - `ParseError::UsnOutOfRange`.
- `crates/ntfs/src/testvol.rs` (Windows, `test-fixtures` feature): `TestVolume::create(size_mib)` uses diskpart to create and attach an expandable `.vhdx` in `RUNNER_TEMP`/temp, run `convert mbr noerr`, make a primary partition, quick-format it NTFS with the label `WBTEST`, and assign the highest free letter from Z: to G:. Other methods: `create_journal(m, a)`, `delete_journal()` (`fsutil … /d`, then waits until the journal is gone) and `path()`. Drop detaches the VHD and deletes the file. Volume creation is serialised within the process. 3.3, 4.1 and 4.2 can use it as a dev-dependency.
- `crates/ntfs/Cargo.toml`: a self dev-dependency with `test-fixtures`, so this crate's integration tests get `testvol`. No new external dependencies. `Cargo.lock` changed by one line (the self edge).
- `crates/ntfs/tests/journal_vhd.rs` (6 `#[ignore]` elevated tests; each test gets its own VHD and they run one at a time):
  - identity, root and enumeration;
  - create, modify, rename, move and delete;
  - coalescing within one batch;
  - wrap: a 1 MiB journal plus churn until `FirstUsn` passes the checkpoint, then the kernel returns `ERROR_JOURNAL_ENTRY_DELETED` and the source returns `JournalWrapped`;
  - `fsutil usn deletejournal`, then `JournalMissing`; recreate, then `JournalRecreated`;
  - foreign, garbage and future checkpoints → `CheckpointMismatch`.
- `ci.yml` is unchanged: the existing elevated step `cargo test -p whereabouts-ntfs -- --ignored` already runs these tests.

## Decisions proposed
- **Coalescing is per file per batch**, not per close session. One event per file and batch (two for rename + write) matches the `Modified` contract ("once per batch"). A file still open at the end of a batch is reported with what is known so far. When its close record arrives later, it is reported again, which consumers handle idempotently (D-29). Debouncing across batches stays with 3.3.
- **Renames split across batches are carried in the checkpoint** (≤ 64 `PendingRename`s), so the pair is never lost. A new-name record that can't be paired becomes `Created(final)`. D-29 replay already requires consumers to treat `Created` of a known FRN as an upsert. Carried entries are dropped once a non-empty batch doesn't resolve them, because the new-name record follows the old one immediately.
- **Delete wins**, even for files created in the same batch, because enumeration could have reported them between the checkpoint and the delete.
- **A malformed journal record → `FullRescanRequired(Other)`** instead of skipping it, since a skipped record means a silently wrong index. A rescan can't loop, because its checkpoint is taken after the bad record.
- **No journal, no history.** Enumeration works without a journal. The checkpoint records that, and `changes` asks for a rescan until a journal exists. The source never creates one (D-31). A journal that appeared after the checkpoint → `JournalRecreated`.
- **Root record**: own parent, empty name, `DIRECTORY`. 2.1 may also seed the root, and `Created` for a known FRN is an upsert anyway.

## Deviations / contract changes
- None to frozen contracts. The `ntfs` API is additive: new modules and types, new `Volume` methods, and new variants on the `#[non_exhaustive]` `Error`/`ParseError`. `RawRecord`, `RecordIter` and `Enumerator` are unchanged for 2.7.
- `HARD_LINK_CHANGE` is reported as `Modified` with the link name from the record (documented; extra links are not tracked in M0).

## Follow-ups
- **3.3**: poll `changes` until a batch is empty (batches are capped by `max_batch_bytes`). Commit `batch.checkpoint` only after applying the batch, because it may carry pending renames. Debounce writes in progress, since an open file is reported before its close. Decide whether and when to create a journal on a volume that has none.
- **2.1 / 3.3**: apply a whole batch before resolving paths. A file moved into a directory created later in the same batch can come before that directory.
- **4.2**: `TestVolume` plus `create_journal(m, a)` covers the wrap and recreate scenarios. Our own reads producing no USN events is still to be tested there.
- **#25** (mount points, GUID paths) is still open: `identity().key` already is the GUID path, so the catalog can match volumes across letter changes.
- Lib docs on Linux: the Windows-only items in the `lib.rs` table are no longer intra-doc links. Before this change, `cargo doc --target x86_64-unknown-linux-gnu` failed with `-D warnings`.
