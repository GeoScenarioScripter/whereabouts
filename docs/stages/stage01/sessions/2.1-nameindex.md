# stage01/2.1 — nameindex
Date: 2026-10-20 · Issue: #5 · PR: #35 · Verification reached: V1 (local Windows; CI for Linux)

**Context**: wave 2 component on the 1.1 contracts (`FileRecord`, `FileName`, `Frn`, `Checkpoint`, `SourceEvent`). Spec: string pool + entry columns, case-folded copy, FRN map, path reconstruction with guards, upsert/delete/rename with tombstones + compaction, substring/wildcard/extension/path search with a parallel scan, a checksummed snapshot with an embedded `Checkpoint`, and 1M/5M benchmarks (Q-18 inputs). Wave 1 hand-offs: seed the root (D-31), orphans under `$Extend`, zero-copy ingestion, measure #26.

## What changed
- `crates/nameindex/src/`
  - `index.rs`: `NameIndex` with struct-of-arrays columns (FRN 8 B, parent entry 4, name offset 4 + length 2, folded segment 4, extension offset 2, attributes 4, live flag 1). There are two pools: the original names (WTF-8, D-28) and the folded names, NUL-separated, with a segment table (start + owner, 8 B).
    - The root is seeded at construction (`NameIndex::new(root)`, from `Source::root()` / `Volume::root_frn()`, D-31).
    - `insert`, `insert_wtf8` (validated) and `insert_utf16le` (zero-copy from `UsnRecord::name_utf16le()`) are all **upserts by FRN**, so replay is idempotent. `remove` tombstones; `apply(&SourceEvent)`; `compact()` (invalidates `EntryId`s, never FRNs); `needs_compaction()`; `stats()` (heap bytes from buffer capacities).
    - Out-of-order parents: children wait in a pending table and are linked when the parent FRN appears. Orphans stay orphans. A tombstoned parent forwards to a live entry with the same FRN, so delete + recreate re-links its children.
    - `path()` returns `\dir\name` (WTF-8, leading `\`, root = `\`), or `PathError::{NotFound, Orphan, Cycle}`. Any chain deeper than `MAX_DEPTH` (16,384, the NTFS path limit) counts as a cycle.
  - `frnmap.rs`: FRN → entry map. It's a dense `u32` table indexed by MFT record number (4 B per record), with the full FRN verified against the column. A hash-map overflow takes sparse IDs (growth capped at 8 × entries + 64 Ki) and same-record/different-sequence collisions.
  - `fold.rs`: case folding is a 1:1 code-point map, `lower(upper(c))` with fallbacks (`ς`/`σ`/`Σ` merge, `ẞ` → `ß`, `ß` and `İ` stay). Tested idempotent over all of Unicode. Also: UTF-16LE → WTF-8, WTF-8 validation, and an anchored wildcard matcher (`*`, `?` = one code point, never splits a UTF-8 sequence). Nothing in it can panic on malformed bytes.
  - `search.rs`: `Query { text, mode: Substring|Wildcard, match_path, extensions, kind, limit }` built structurally (syntax is Q-11); `SearchResults { hits, total }`.
    - Name mode with a literal: one `memchr::memmem` pass over the folded pool, in rayon chunks; hits map to segments by binary search; stale segments are skipped.
    - No literal (filter-only, `*`): a column scan.
    - Path mode: a per-query atomic memo per directory ("does its path contain the needle"). An entry matches if its parent's path does, or if the needle occurs in (last `len−1` bytes of parent path) + `\` + name. A needle without `\` only checks the name. A wildcard builds the full folded path only for prefiltered candidates.
    - Orphans and cycles have no path, so they never match in path mode; they are still found by name.
  - `snapshot.rs`: format v1 (layout table in the module docs): `WBNISNAP` magic, version, root FRN/attrs, the embedded `Checkpoint::to_bytes()`, one entry record per live entry (FRN, parent FRN, attrs, name), then a CRC-32.
    - Loading re-inserts through the normal upsert path. It validates WTF-8, name length, duplicate/root FRNs, count, trailing bytes and CRC, and caps preallocation at 1 Mi entries whatever the header claims.
    - `save_snapshot` writes `<path>.tmp`, fsyncs and renames it into place.
  - `synth.rs` (public, not production API): a deterministic synthetic volume shaped on 1.3's C: numbers. It has 15 % directories, depth ≤ 14 with sibling locality, ~24 B average names (words, IMG/DSC/tile counters, hashes, GUIDs, WinSxS-style names, ~2 % non-ASCII), a Windows-like extension mix with a few GIS formats, and dense ascending record numbers. 4.3 can reuse it.
- Tests: `tests/model.rs` is a proptest of 512 cases. Up to 60 random upserts (both name paths), removes, compactions and snapshot round trips run over 32 FRNs that share 16 record numbers, with missing parents, self-parents and cycles. After each case, paths, names, entry listing and up to 24 random queries per case must equal a naive model (`tests/common`: BTreeMap, visited-set walks, code-point DP wildcard). `tests/behaviour.rs` has targeted cases and a 120k-entry synthetic volume (multi-chunk parallel scans, renamed entries) checked against brute force. `tests/snapshot.rs` covers round trips (with checkpoint, empty, via file), every truncation, every single-byte flip ×3 patterns, specific errors, and content that is invalid but carries a valid CRC.
- `benches/search.rs` (criterion, 1M + 5M, 14 queries), `benches/ingest.rs` (#26), `examples/measure.rs` (memory/entry, snapshot, latency percentiles).
- Root `Cargo.toml` `[workspace.dependencies]` additions:
  - `crc32fast` 1.5.2: snapshot checksum, SIMD.
  - `memchr` 2.8.3: memmem; it was already in the lock graph.
  - `rayon` 1.12.0: the scan pool, which keeps per-query thread spawn off the typing path.
  - Dev only: `criterion` 0.8.2 (no default features) and `proptest` 1.12.0.

  All are MIT/Apache (memchr is Unlicense OR MIT) and pure Rust. `whereabouts-ntfs` (`test-fixtures`) is a dev-dependency only, used by the ingest bench.

## #26 — borrowed `FileRecord` view in `RecordSink`
`cargo bench -p whereabouts-nameindex --bench ingest`. The input is 1M synthetic records as real `FSCTL_ENUM_USN_DATA` output (1 MiB batches), walked with `RecordIter`:

| Variant | Time / 1M | Per record |
|---|---|---|
| `walk_only`: parse the buffers | 9.7 ms | 10 ns |
| `owned_records_only`: + `FileName::from_utf16` + `FileRecord` + `dyn RecordSink`, no index | 115 ms | 115 ns |
| `owned_sink_insert`: today's contract, into the index | 266 ms | 266 ns |
| `borrowed_insert`: `insert_utf16le` straight from the buffer | 184 ms | 184 ns |

A borrowed view saves about **82 ns per record (31 % of ingestion)**, roughly 0.1 s per 1.34M-record volume. That compares with 2.6 s of kernel time per 1.34M records warm and 40 s cold on CI, and 41 s on the owner's D: (1.3 note, G1). So it's about 3 % of a warm enumeration and under 0.3 % of a cold one.

**Recommendation: don't change the `RecordSink` contract now.** Revisit only if 2.7's raw `$MFT` reader brings enumeration down to the same order as ingestion, around 1 s per million records. If it does, the change is additive and non-breaking:
- add `RecordRef<'a> { frn, parent, name_utf16le: &'a [u8], attrs }`;
- add a provided method `RecordSink::accept_ref(&mut self, r: RecordRef<'_>) -> ControlFlow<()>` that defaults to building a `FileRecord` and calling `accept`;
- the name index overrides it with `insert_utf16le`, which already exists.

That would be a `whereabouts-source` change, so it belongs to the orchestrator or 3.3, not this session.

## Decisions proposed
- **Case folding = 1:1 code-point `lower(upper(c))`** with single-char fallbacks (`fold_char`); not NTFS's upcase table, not full Unicode case folding (which expands `ß` → `ss` and would make `?` count characters that aren't there). Queries are folded the same way.
- **Path format and path-mode haystack** = volume-relative, leading `\`, `\` separators (`\data\roads.shp`; root `\`). Consumers prefix the drive. In path mode `*` also matches `\`.
- **Orphans are searchable by name, never by path**; `path()` reports `Orphan`. The query layer (4.1) decides whether to hide them (e.g. drop results whose path is `Orphan`, or have the pipeline seed `$Extend` like the root).
- **Snapshot v1 stores entries by FRN and reloads through upsert** (validation for free, layout-independent) instead of dumping columns; costs ~1.1 s load at 5M. See follow-ups.
- **Upsert semantics for every event** (Created/Modified/Renamed); `EntryId`s are stable until `compact()`; FRNs are the durable identity.

## Deviations / contract changes
- None. No core/source type changed. The #26 measurement is reported below as a proposal, not adopted.
- Spec "parent index": stored as an entry index, plus a pending table for parents not seen yet, plus forwarding through tombstones. That's needed because enumeration order isn't topological.
- Results are in deterministic but unspecified order, and `total` always counts every hit (no early exit under `limit`). Ranking is out of scope.

## Follow-ups
- **#26 / contract (orchestrator)**: see the measurement above. A proposal for `whereabouts-source` is in the #26 section.
- **4.1 (query)**: hide or mark orphans, and load the snapshot at startup. Snapshot load is about 1.1 s per 5M entries.
- **4.3 / later perf** (only if Q-18 targets demand it):
  - (a) A column-dump snapshot v2 for faster load.
  - (b) Share bytes between the name pool and the folded pool when they're equal (~20 B/entry less).
  - (c) Pack the live flag into `attrs`.
  - (d) An extension index for filter-only queries (12 ms at 5M today).
  - (e) A cheaper path-mode memo (per-query `Vec<AtomicU8>` + suffix walks; 50–130 ms at 5M).
  - (f) A faster 1-character path (per-hit cost dominates).
- **3.3 (pipeline)**: call `compact()` when `needs_compaction()` after a change batch, and treat `EntryId`s as invalid after it. On `IndexError::CapacityExceeded`, compact and retry, or rescan.
- Hard links: one name per FRN (last upsert wins), consistent with M0's documented limitation.
