# stage01/1.2 — oracle-corpus
Date: 2026-10-19 · Issue: #2 · PR: (see PR) · Verification reached: V2 (local, Windows + Docker) — CI evidence in the PR

**Context**: no dependencies. The spec asked for a committed SHP/GPKG/GeoTIFF corpus covering the listed edge cases, built inside a pinned GDAL container; one normalized GDAL oracle record per case; a `workflow_dispatch` regeneration workflow; and the `tests/oracle` crate (record types, tolerance-aware comparison, an empty adapter registry, a per-format report, and a baseline-gated agreement test).

## What changed
- **Corpus** (`tests/corpus/`): `manifest.toml` lists 47 cases: 46 committed (21 shapefile, 11 geopackage, 14 geotiff; 45 synthetic + 1 real-world Natural Earth 110m land) and 1 external (Natural Earth 10m countries, about 9.7 MB). The committed data is 1.14 MB. There are 7 deliberately corrupt cases (3 SHP, 2 GPKG, 2 TIFF). Tag vocabulary and record format are in `tests/corpus/README.md`.
- **Generation**: `scripts/generate.sh` runs `generate.py` and `golden.py` in `ghcr.io/osgeo/gdal:ubuntu-small-3.13.3@sha256:64250faf…` with `--platform linux/amd64` (GDAL 3.13.3, PROJ 9.8.1). `generate.py` has one builder per synthetic case and checks the files it produces against the manifest's `files` list. To keep runs deterministic it pins the DBF date and the GPKG `last_change`, and computes all coordinates and pixels in closed form.
- **Goldens** (`expected/<id>.json`, schema 1): per-layer geometry type plus Z/M, exact count, the *true* extent alongside the *declared* extent (SHP header / `gpkg_contents`), raster facts (incl. `georef_source`, PixelIsPoint, BigTIFF, COG layout, overviews, NaN nodata), fields, DBF encoding signals, and CRS. The CRS part has the raw definition text plus its kind, WKT2, EPSG plus method/confidence/candidates (identified from the *raw* text), and a status. The WGS84 extent comes from `TransformBounds` with 21-point densification and an antimeridian flag.
- **External**: `scripts/fetch-external.{sh,ps1}` and `scripts/external-files.txt` (sha256, destination path, URL pinned to a commit). Both scripts were tested: fetch, the cached path, and re-fetching a deleted file.
- **Workflow** `.github/workflows/oracle-golden.yml`: `workflow_dispatch` with `verify` and `external` inputs; uploads the `oracle-corpus` artifact. It **also runs on PRs that touch `tests/corpus/scripts/**`, the manifest or the workflow**, and fails on drift (this is an addition to the spec).
- **`tests/oracle` crate**: `manifest` (validated: unique ids, plain file names only so nothing can traverse paths, anchor in files), `record` (oracle types with `deny_unknown_fields`; `NativeRecord`/`NativeLayer`/`NativeRaster` for adapters), `compare` (`Check` enum, `Tolerances`, per-check verdicts), `adapters` (`ADAPTERS` is empty; `ReadFn = fn(&ResolvedCase) -> Option<NativeRecord>`; panics are caught and reported as a hard failure), `report` (markdown per format), `baseline` (`baseline.toml`). `tests/agreement.rs` (`harness = false`) always prints the report and appends it to `$GITHUB_STEP_SUMMARY` in CI. `tests/corpus.rs` holds the integrity tests. `toml` is a crate-local dependency, so the root `Cargo.toml` is untouched. `Cargo.lock` is committed (first build).

## Decisions proposed
- **Oracle tolerances**: native extent |Δ| ≤ max(1e-6, 1e-9·|v|). WGS84: each edge within 0.01°, longitude edges compared modulo 360, **and** the longitude span (with crossing boxes wrapped) within 0.02°, so that a collapsed or inverted box at ±180° can't match the full globe. Raster resolution relative 1e-9 (goldens write it unrounded). Counts and EPSG exact. The 0.01° bound leaves room for proj4rs vs PROJ (no grid shifts, D-09). Q-14 may tighten it.
- **Baseline**: `status`/`layers` 1.0; `geometry_type`/`feature_count`/`native_extent`/`raster` 0.98 (exit criterion 4); `epsg`/`wgs84_extent` 0.0 until 2.4/4.3 set the Q-14 targets.
- **Comparison semantics**: adapters declare the checks they are held to. For a declared check, a missing native value disagrees with an oracle value. Checks are skipped where they don't apply (no geometry/count check on rasters, no extent/EPSG check on attribute tables). Corrupt-tagged cases and cases GDAL refused are compared on status only (`Error`/`Partial` expected). Partial agrees with either verdict. Rates with nothing compared are not enforced.
- **Extent convention**: native readers are compared against the *true* data extent, not the declared one. Stale `gpkg_contents` bounds therefore need the R-tree fallback, and an empty SHP (header zeros) must report no extent. Raster extents use GDAL's PixelIsArea geotransform corners, so PixelIsPoint files must be shifted by half a pixel.
- **EPSG identification in goldens** runs on the raw definition (authority → `AutoIdentifyEPSG` → `FindMatches` ≥ 70). The ESRI custom-name UTM case identifies as 32633 at confidence 70.
- **Layer naming**: SHP/GeoTIFF layer = file stem; GPKG = `table_name`; all `gpkg_contents` rows are layers, including attributes and tiles.
- **GDAL image**: pin `ubuntu-small-3.13.3` by digest on `linux/amd64`. Bumping it is a reviewed diff.

## Deviations / contract changes
- (none to frozen contracts.) Additions beyond the spec: `fields`/`encoding`/`declared_extent`/`messages` in the record; the PR trigger on the golden workflow; a committed real-world case.
- `gpkg_undefined_srs` rewrites the layer to the spec's `srs_id -1`, because GDAL 3.13 writes its own `99999` "Undefined SRS". Engineering/undefined CRSs are recorded as `crs.status = missing`.
- GDAL's GTiff driver ignores a world-file `.prj`. `golden.py` parses it with OSR (`crs.source = "prj"`) because that is the behaviour we want.
