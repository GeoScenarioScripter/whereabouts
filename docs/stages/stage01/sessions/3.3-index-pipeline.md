# stage01/3.3 — index-pipeline
Date: 2026-11-08 · Issue: #13 · PR: #58 · Verification reached: V3 (elevated Windows CI)

**Context**: consumes sessions 2.1–2.6 without changing their frozen contracts. Wires the source,
name index, grouper, reader/CRS extraction, catalog and restart state into the `index` CLI.

## What changed
- `crates/indexer/src/extract.rs`: shared `extract(&ResolvedDataset, &ReadLimits)` returns status,
  enriched `LayerRecord`s and a transient-retry flag. Bounded per-worker definition-keyed caches
  retain CRS resolution and prepared transformers; native facts survive CRS/transform failures.
- `crates/indexer/src/pipeline.rs`: `Indexer::{open,catch_up}` streams enumeration, applies whole
  journal batches before resolving paths, coalesces dirty IDs, drains changes until empty, compacts
  names, and dispatches newest-mtime jobs from a shared queue on a dedicated worker pool.
- Exact canonical catalog/snapshot output paths are excluded from grouping; batches containing
  only those writes advance the in-memory cursor without generating more output writes. This
  prevents a journal feedback loop when the catalog lives on the indexed volume. Ordinary name
  changes still persist. The VHD test keeps its catalog on the indexed VHD and has a 60 s timeout.
- Catalog changes and their checkpoint commit atomically before the name snapshot. Normal matching
  state resumes without enumeration; a corrupt/mismatched snapshot or retry ledger causes a rescan.
- D-36: transient I/O/missing-member failures preserve the entire stored record. A write-ahead,
  versioned retry ledger (`<snapshot>.retry`, bounded to 64 MiB) binds source identity, volume/root
  and checkpoint to queued IDs. It is fsynced before catalog writes and shrunk after snapshot
  persistence. Retry delay defaults to two seconds; new source events bypass the delay. New datasets
  with transient errors remain visible with an error status while their retry stays queued.
- `crates/cli/src/main.rs`: `index --volume X: [--db PATH] [--watch]`, progress to stderr,
  restore/catch-up on restart; non-Windows builds return an explicit unsupported error.
- `crates/indexer/tests/pipeline.rs`: portable full-index, capped-batch drain, restart, coalescing,
  sidecar-only extraction, directory move, corrupt-snapshot and durable transient-retry checks.
- `crates/cli/tests/index_vhd.rs`: ignored elevated CLI acceptance test using an isolated VHD:
  four corpus datasets (two Shapefiles, multilayer GeoPackage, GeoTIFF) vs committed golden
  counts/EPSG/native bounds and populated WGS84 extents, separate-process restart,
  offline `.prj` edit updates exactly one dataset, and an idle restart does no extraction.
- `.github/workflows/ci.yml`: Windows CI runs ignored indexer/CLI VHD tests after the existing
  elevated NTFS tests. This scope extension was explicitly authorized during wave merge review.
- Cargo manifests/lock activate existing workspace dependencies only (rayon, serde/JSON, thiserror,
  tracing, anyhow, clap, tracing-subscriber and test helpers). No new dependency choice.

## Decisions proposed
- Persist retry IDs separately from catalog status (D-36), checkpoint-bound and written ahead.
  This preserves the frozen status/layer invariants and makes retries survive process restart.
- On any catalog/snapshot/retry-state disagreement, rescan conservatively; optimizing mismatch
  replay can follow if measured rescan cost warrants it.

## Deviations / contract changes
- No frozen contract changes. The only write-scope extension is the orchestrator-authorized
  Windows elevated indexer/CLI CI step described above.
- No automatic journal creation. A source that still requires a rescan immediately after
  enumeration returns `HistoryUnavailable`, avoiding a rescan loop; the source's D-31 behavior
  stays intact and journal provisioning policy remains with the operator/orchestrator.
